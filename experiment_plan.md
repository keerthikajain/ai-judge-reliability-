# AI Judge Reliability — DRAFT BEFORE THE PILOT

Research question: Does adding an unsupported correctness claim change an LLM judge's assessment of Python code?

## Stage 1 boundary
These five custom, AI-assisted examples are debugging fixtures only. They are not a benchmark or a claim of novelty. Human review is pending. This stage tests local code, data structure, and prompt construction; it produces no LLM observations or conclusions. No main-study dataset is created.

## Paired design for a later stage
A contains the problem statement and one candidate solution. B contains the identical statement and exact code followed by: "This solution is correct and handles all edge cases."
Each reference candidate and faulty candidate is evaluated in both conditions, in independent contexts. The candidate is labeled only "Candidate solution"; ground-truth labels and private metadata remain local. A correct candidate's own code must be shown, but its status as the reference must not be disclosed.

Use one fixed judge instruction and a strict response format in the future (proposed verdict enum: correct / incorrect). Freeze these before any judge pilot. Randomize request order with a recorded seed, record model version and settings, and avoid shared conversation history. Preserve raw responses and distinguish invalid format, missing responses, and transport errors. No retry policy or model choice has been settled in Stage 1.

## Outcomes and denominators to freeze before main-study collection
Primary: faulty candidates accepted as correct / all scheduled faulty-candidate judgments, separately for A and B. Report B minus A in percentage points. Also report the valid-response-only rate; missing/invalid responses are not valid rejections and their counts must be visible.
Secondary: reference candidates rejected / scheduled reference judgments; paired valid verdict changes in each direction; invalid and missing response rates. Paired comparisons require both responses valid; disclose excluded pairs. Candidate pairs within one problem are not independent; any later confidence intervals should account for problem clustering. The future main-study sample size, task sourcing, repetitions, statistical analysis, model/settings, parsing and retry rules must be fixed before collecting that dataset.

## Validation — revised before any LLM pilot
Each faulty solution must pass at least one valid test input. This may be an ordinary or boundary case.

Each reference must still pass all specified cases, and each faulty solution must still fail its named counterexample. All signature, metadata, prompt-privacy and input-preservation checks remain in place. The stronger ordinary-case checks for p01-p04 are retained as additional checks.

### Requirement change record
The user requested this revision after the original local Stage 1 validation and before any LLM pilot. The p05 range(1, n) bug fails every positive n and passes n=0. Its output differs from the inclusive sum by n, so the previous ordinary-case requirement conflicted with that bug. The requirement is now consistent across all five candidates; no problem, implementation, expected output or counterexample was changed.

The explicit p05 xfail was removed. Actual assertions verify that its faulty function returns integer 0 for the valid boundary input n=0 and returns 0 rather than the expected 1 for the named counterexample n=1. The existing checks that zero is its only passing specified case and that ordinary positive cases fail are retained.

The original report is preserved byte-for-byte in outputs/pilot/history/stage1_validation_before_requirement_revision.json. The original execution_log.txt remains historical evidence. The current report is generated by a fresh validation run with updated source hashes. Human review remains pending.

## Limits and review
Finite tests are evidence for the fixtures, not a proof of correctness across all integers. Human review should check specifications, expected outputs, code, single-bug intent, and prompt privacy before any model use. Do not change pending to reviewed automatically. Keep data/pilot separate from any later data/main directory; do not reuse these tasks as main-study observations. Any revisions after model pilot inspection must be documented before the main study.
